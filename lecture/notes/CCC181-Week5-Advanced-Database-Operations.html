SQL from Flask

Two ways to send SQL from Flask

Raw SQL with text()

from sqlalchemy import text

sql = text("""
    SELECT id, status FROM tickets
    WHERE user_id = :uid
    ORDER BY created_at DESC
""")
rows = db.session.execute(sql, {"uid": 3}).all()

ORM select()

stmt = (db.select(Ticket)
        .filter_by(user_id=3)
        .order_by(Ticket.created_at.desc()))
tickets = db.session.scalars(stmt).all()

Both send :uid as a bound parameter. Never build SQL with f-strings.

This week we write a lot of SQL, so first establish how to run it from Flask. text() lets you write exact PostgreSQL SQL, including window functions and CTEs, while still using named parameters, which the driver sends separately from the SQL so input can never become code. The ORM builds the same SQL from Python. A good workflow: develop and debug the query in psql or a GUI such as pgAdmin or DBeaver, then move it into Flask with text() or translate it to select().

INNER JOIN and LEFT JOIN

INNER JOIN

Only rows that match on both sides. A ticket with its user and service.

FROM tickets t
JOIN users u ON u.id = t.user_id

LEFT JOIN

Every row on the left, matched or not. Every service, even with no tickets.

04

A join combines rows from two tables using the foreign key relationship from our ERD. The difference only shows when something has no match. For a staff report that lists every service and how many tickets it had today, an inner join silently drops Dental because it had zero tickets; a left join keeps it and fills the ticket columns with NULL. Ask before writing any join: do I want rows without a match? RIGHT and FULL joins exist but are rarely needed; you can usually swap the table order and use LEFT.

The staff dashboard needs three tables

staff dashboard query

SELECT t.id,
       u.name  AS student,
       s.name  AS service,
       t.created_at
FROM tickets t
JOIN users u    ON u.id = t.user_id
JOIN services s ON s.id = t.service_id
WHERE t.status = 'waiting'
ORDER BY t.created_at;

Aggregates

GROUP BY: from rows to summaries

average wait per service, last 7 days

SELECT s.name,
       COUNT(*)                     AS served,
       AVG(t.called_at - t.created_at) AS avg_wait
FROM tickets t
JOIN services s ON s.id = t.service_id
WHERE t.called_at IS NOT NULL
  AND t.created_at >= CURRENT_DATE - 7
GROUP BY s.name
HAVING COUNT(*) >= 5
ORDER BY avg_wait DESC;

Aggregate functions

COUNT, SUM, AVG, MIN, MAX

WHERE vs HAVING

WHERE filters rows before grouping; HAVING filters groups after

Interval math

called_at - created_at is an interval, e.g. 00:18:30

CCC181 · Week 5 · Advanced database operations

06

This is the first real report the clinic asked for in our Week 1 interviews: which services make students wait the longest. GROUP BY collapses many rows into one row per group, and aggregates summarize each group. The order of evaluation explains WHERE versus HAVING: FROM and JOIN, then WHERE, then GROUP BY, then HAVING, then SELECT, then ORDER BY. HAVING COUNT(*) >= 5 hides services with too few tickets for a meaningful average. Subtracting two timestamps gives an interval, and AVG works on intervals directly in PostgreSQL.

Conditional counts with FILTER

daily summary

       COUNT(*)                                       AS joined,
       COUNT(*) FILTER (WHERE status = 'served')     AS served,
       COUNT(*) FILTER (WHERE status = 'left')       AS left_queue
FROM tickets
GROUP BY 1
ORDER BY 1 DESC;

FILTER is a PostgreSQL feature that counts only the rows matching a condition inside one aggregate, so one pass over the table produces several numbers. The portable equivalent is SUM(CASE WHEN status = 'served' THEN 1 ELSE 0 END). date_trunc rounds a timestamp down to the day, week or month. GROUP BY 1 means group by the first selected column. The sample output is illustrative; students will see their own seeded data. A left_queue count is a useful product metric: it tells the clinic how often students give up.

Subqueries

Subqueries: a query inside a query

Scalar: one value

SELECT id FROM tickets
WHERE status = 'waiting'
  AND now() - created_at > (
    SELECT AVG(called_at - created_at)
    FROM tickets
    WHERE called_at IS NOT NULL);

EXISTS: is there any?

SELECT s.name FROM services s
WHERE EXISTS (
  SELECT 1 FROM tickets t
  WHERE t.service_id = s.id
    AND t.status = 'waiting');

Left: tickets waiting longer than average. Right: services with someone in line right now.

CCC181 · Week 5 · Advanced database operations

08

A scalar subquery returns a single value and can be used wherever a value is expected, like the average wait here. EXISTS checks whether at least one matching row exists and stops at the first one, which makes it efficient; NOT EXISTS answers questions like which users have never joined the queue. The EXISTS subquery is correlated because it refers to s.id from the outer query. Subqueries can also appear in FROM, which leads to the cleaner version: CTEs, next slide.

CTEs

Common table expressions: name each step

served rate, last 7 days

WITH daily AS (
  SELECT date_trunc('day', created_at) AS day,
         COUNT(*) AS joined,
         COUNT(*) FILTER (WHERE status = 'served') AS served
  FROM tickets
  GROUP BY 1
)
SELECT day, joined, served,
       ROUND(100.0 * served / joined, 1) AS served_pct
FROM daily
ORDER BY day DESC
LIMIT 7;

WITH name AS (…) defines a temporary result you can query like a table.

Readable

Each step has a name, like variables in Python

Reusable

Refer to the same CTE several times in the query

Recursive

WITH RECURSIVE walks trees and hierarchies

CCC181 · Week 5 · Advanced database operations

09

A CTE breaks a complicated query into named steps that read top to bottom. Here the first step summarizes each day and the second computes a percentage from it. Note 100.0 instead of 100: integer division in SQL truncates, so 55 / 64 would be 0. You can chain several CTEs separated by commas. Recursive CTEs are beyond our MVPs, but useful for categories inside categories or organization charts. In PostgreSQL 12 and later, simple CTEs are inlined by the planner, so they are not slower than the equivalent subquery.

Window functions

Ana's position: ROW_NUMBER() OVER

queue position

WITH line AS (
  SELECT id,
         ROW_NUMBER() OVER (
           PARTITION BY service_id
           ORDER BY created_at, id
         ) AS position
  FROM tickets
  WHERE status = 'waiting'
)
SELECT position FROM line
WHERE id = :ticket_id;

PARTITION BY

Restart the numbering for each service's line

ORDER BY created_at, id

First come, first served; id breaks ties

Why the CTE?

Number all waiting tickets first, then pick Ana's. Filtering first would make her always #1

CCC181 · Week 5 · Advanced database operations

10

This is the payoff of storing facts instead of positions. A window function computes a value for each row using other rows in its window, without collapsing them. ROW_NUMBER numbers the waiting tickets of each service in order of arrival. The CTE matters: WHERE runs before window functions, so putting id = :ticket_id in the same query would leave one row, numbered 1. The id tiebreaker matters too: tickets created in the same transaction share the same now() value. Students should put this query behind the My place page from Week 3.

CCC181 · Week 5 · Advanced database operations

11

Side by side: GROUP BY gives one row per service, while the window version keeps one row per ticket and adds both the position and the total in line, so the My place page can say you are 2 of 3. LAG and LEAD are useful for time between consecutive tickets, which estimates service speed. Window functions are standard SQL and supported by PostgreSQL, MySQL 8 and SQLite 3.25 or later.

Transactions

Transactions: all or nothing

Definition

A transaction groups statements so they succeed together or fail together, isolated from other users until COMMIT.

Atomic

All steps or none

Consistent

Constraints always hold

Isolated

Others don't see half-done work

Durable

Committed means saved

The race: two nurses press Call next at the same moment. Without care, both get ticket #12 and #13 is skipped or called twice.

CCC181 · Week 5 · Advanced database operations

12

Every db.session.commit() from Week 4 already ended a transaction; SQLAlchemy begins one automatically on the first statement. ACID is the set of guarantees. The race condition is the real problem for ClinicQ: both requests read the oldest waiting ticket before either has updated it, so both call the same student. Atomicity alone does not prevent this; we need to lock the row we picked. Ask students to find the equivalent race in their own MVP: booking the last slot, claiming an item, reserving a room.

Transactions

Call next safely: FOR UPDATE SKIP LOCKED

in SQL

BEGIN;
SELECT id FROM tickets
WHERE service_id = 1 AND status = 'waiting'
ORDER BY created_at, id
LIMIT 1
FOR UPDATE SKIP LOCKED;

UPDATE tickets
SET status = 'called', called_at = now()
WHERE id = 12;
COMMIT;

in Flask

def call_next(service_id):
    stmt = (db.select(Ticket)
            .filter_by(service_id=service_id,
                       status="waiting")
            .order_by(Ticket.created_at, Ticket.id)
            .limit(1)
            .with_for_update(skip_locked=True))
    t = db.session.scalars(stmt).first()
    if t is None:
        return None
    t.status = "called"
    t.called_at = func.now()
    db.session.commit()
    return t

PostgreSQL documentation, SELECT: The Locking Clause

13

FOR UPDATE locks the selected row until the transaction ends. SKIP LOCKED tells a second transaction to skip rows another transaction has locked instead of waiting, so the second nurse simply gets the next ticket. This is the standard PostgreSQL pattern for job queues. Demo it with two psql windows: run BEGIN and the SELECT in both; the second returns ticket 13. In Flask, with_for_update(skip_locked=True) adds the same clause, and commit releases the lock. If anything fails before commit, rollback releases it and nothing changes.

Transactions

Isolation levels in PostgreSQL

LevelSeesUse it when
Read Committed (default)Data committed before each statement startedMost web requests; add row locks where races matter
Repeatable ReadOne snapshot for the whole transactionReports that must be internally consistent
SerializableAs if transactions ran one at a timeComplex invariants; be ready to retry on failure

Keep transactions short

Locks are held until COMMIT. Never wait for user input or call a slow external API inside one.

Retry on conflict

Serializable and deadlocks raise errors on purpose; catch them, roll back and try again.

PostgreSQL documentation, Chapter 13: Concurrency Control

14

Isolation decides what a transaction can see of other concurrent transactions. PostgreSQL's default, Read Committed, is right for almost all MVP requests; explicit row locks like the previous slide handle the specific races. Repeatable Read gives a stable snapshot, useful for a report that runs several queries. Serializable is the strongest and makes PostgreSQL abort transactions that could produce an anomaly, so code must retry. The practical rules are on the bottom: short transactions, and handle conflicts rather than ignoring them.

Indexes

Indexes: the book index for your table

Without an index, PostgreSQL reads every row to find matches: a sequential scan.

A B-tree index keeps column values sorted with pointers to rows, so lookups jump straight there.

Primary keys and UNIQUE columns are indexed automatically. Foreign keys are not.

Speeds up

WHERE, JOIN … ON, ORDER BY on indexed columns

Costs

Disk space, and slower INSERT and UPDATE: every index is updated too

Rule

Index for queries you actually run, then measure

CCC181 · Week 5 · Advanced database operations

15

Like the index at the back of a textbook: instead of reading every page for 'transaction', you look it up and jump to page 212. Each index makes reads faster for matching queries and writes slightly slower, so do not index every column. The foreign key point surprises students: PostgreSQL creates indexes for primary keys and unique constraints, but not for foreign key columns, so tickets.service_id and tickets.user_id need indexes if you join or filter on them, which we do constantly.

Indexes

Make enough data to measure

200,000 test tickets (assumes users 1–50 and services 1–4 exist)

INSERT INTO tickets (user_id, service_id, status, created_at)
SELECT 1 + (random() * 49)::int,
       1 + (random() * 3)::int,
       (ARRAY['waiting', 'served', 'served', 'left'])[1 + (random() * 3)::int],
       now() - random() * INTERVAL '90 days'
FROM generate_series(1, 200000);

Why

With 20 rows every query is instant. Performance problems only appear at realistic sizes.

Where

Only in your local or test database. Never seed fake data into a shared or deployed one.

generate_series produces a row per number, and random() spreads the values. This creates three months of plausible traffic in a few seconds. PostgreSQL documentation: Using EXPLAIN · Partial Indexes

17

EXPLAIN shows the plan PostgreSQL chooses; EXPLAIN ANALYZE also runs the query and reports actual times and row counts. The outputs here are trimmed for the slide; students should record their own full output and timings as performance evidence. The index is partial: it only contains waiting tickets, which are a small fraction of the table, so it stays tiny and fast, and it is composite: service_id first for the equality filter, created_at second for the ordering, which also removes the sort step. Add indexes through a migration, not by hand, so every environment gets them.

Derive indexes from the queries in your app, not from the schema alone. Column order in a composite index matters: it works like a phone book sorted by last name then first name, useful for last name alone but not for first name alone. Put equality columns first and range or sort columns after. Verify each index with EXPLAIN: if the plan still shows a sequential scan on a large table, the index is not helping and should go.

from sqlalchemy import func

stmt = (
    db.select(Service.name,
              func.count(Ticket.id).label("tickets"))

Every SQL feature from today has an ORM equivalent: func for functions, outerjoin for LEFT JOIN, group_by and having, and over() for window functions. A query that returns plausible numbers is not necessarily correct. Validating means building a tiny dataset where you know the right answer, then checking the query returns it. Edge cases are where SQL bugs hide: empty groups disappear from inner joins, ties make ROW_NUMBER non-deterministic, and aggregates handle NULL differently from what students expect: AVG ignores NULLs, COUNT(column) skips them. The milestone asks for database test evidence; pytest output in the pull request is the simplest form.

03

Students often mix these up, and the HTTP names make it worse: 401 is called Unauthorized but means unauthenticated. Authentication runs first and establishes identity; authorization then checks that identity against the rule for each action. Returning 404 for another user's ticket rather than 403 avoids confirming that ticket 58 exists, which matters when ids are sequential. Ask: what is the worst thing a student could do in ClinicQ today without logging in? Answer: call every student, or delete tickets, through Postman.

Authentication

Store password hashes, never passwords

models.py

from werkzeug.security import (
    generate_password_hash, check_password_hash)

class User(db.Model):
    # ...existing columns
    password_hash: Mapped[str] = mapped_column(String(255))

    def set_password(self, password):
        self.password_hash = generate_password_hash(password)

    def check_password(self, password):
        return check_password_hash(self.password_hash, password)

One-way, salted, slow

A leaked table does not reveal passwords

Already installed

Werkzeug ships with Flask

Never

Plain text, reversible encryption, or a fast hash like plain SHA-256

04

Password hashing turns a password into a value that cannot be reversed; checking hashes the attempt and compares. Werkzeug's helpers add a random salt per user and use a deliberately slow algorithm, so precomputed tables and brute force are impractical. Add the column with a migration. If the MVP can use a campus Google account or Firebase Auth instead, that avoids storing passwords at all, which is even better; justify the choice in the README.

Flask-Login · flask-jwt-extended documentation

05

The web front end and the mobile app authenticate differently because browsers handle cookies automatically and mobile HTTP clients do not. Flask-Login manages server sessions for the Jinja pages; flask-jwt-extended issues signed tokens for the API, which the Week 10 client stores in secure storage and sends in the Authorization header. A JWT is signed, not encrypted: anyone holding it can read its claims, so never put secrets in it, and keep the access token's lifetime short.

@api.post("/auth/login")
def login():
    data = request.get_json(silent=True) or {}
    email = str(data.get("email", "")).strip().lower()
    user = db.session.scalar(db.select(User).filter_by(email=email))
    if user is None or not user.check_password(data.get("password", "")):
        return problem(401, "Wrong email or password.")
    return {"access_token": create_access_token(identity=str(user.id))}
@api.get("/me/tickets")
@jwt_required()
def my_tickets():
    uid = int(get_jwt_identity())
    stmt = db.select(Ticket).filter_by(user_id=uid)
    return [ticket_json(t) for t in db.session.scalars(stmt)]

CCC181 · Week 11 · Advanced features, security, testing and deployment

06

Login checks the hash and returns a signed access token whose identity is the user id as a string, which current versions of flask-jwt-extended require. The same message covers unknown email and wrong password, so attackers cannot discover which emails are registered. jwt_required rejects missing or invalid tokens with 401 before the view runs, and get_jwt_identity tells the view who is calling. The POST /tickets endpoint from Week 6 now takes the user from the token instead of an email in the body. JWT_SECRET_KEY must be long, random and only in environment variables.

Authorization

Enforce roles and ownership on the server

auth.py: role check

def current_user():
    uid = int(get_jwt_identity())
    return db.session.get(User, uid)

def staff_required(view):
    @wraps(view)
    @jwt_required()
    def wrapper(*args, **kwargs):
        if current_user().role != "staff":
            return problem(403, "Clinic staff only.")
        return view(*args, **kwargs)
    return wrapper

api.py: using both

@api.post("/services/<int:sid>/call-next")
@staff_required
def call_next_ticket(sid): ...

@api.get("/tickets/<int:ticket_id>")
@jwt_required()
def get_ticket(ticket_id):
    t = db.get_or_404(Ticket, ticket_id)
    me = current_user()
    if t.user_id != me.id and me.role != "staff":
        abort(404)   # ownership check
    return ticket_json(t)

07

Two kinds of rules: role checks, such as only staff may call the next ticket, implemented once as a decorator; and ownership checks, such as a student may only see or leave their own ticket, which depend on the specific record and must be written inside the view. Missing ownership checks are the most common real-world API vulnerability, known as broken object level authorization: changing /tickets/57 to /tickets/58 in Postman should never show someone else's data. Test both rules with pytest.

import firebase_admin
from firebase_admin import messaging

firebase_admin.initialize_app()  # service account key

def notify_almost_turn(ticket):
    token = ticket.user.fcm_token
    if not token:
        return
    messaging.send(messaging.Message(
        token=token,
        notification=messaging.Notification(
            title="You're 3rd in line",
            body="Head to the clinic now."),
        data={"route": f"/ticket/{ticket.id}"},
    ))

Firebase documentation: Cloud Messaging

The flow: the app asks permission, which Android 13 and later require, gets a device token from FCM and sends it to the Flask API, which stores it on the user. When a staff member calls the next ticket, the server checks who is now third and sends a message through FCM using the Firebase Admin SDK and a service account key kept out of Git. The data payload carries a route so tapping the notification opens /ticket/57 through go_router. This is a justified Firebase use from Week 9: the API cannot reach phones without it.

Privacy

Privacy: health data is sensitive

Data Privacy Act of 2012 (RA 10173)

Personal information may be processed only with transparency, for a legitimate purpose, and in proportion to that purpose. Health information is sensitive personal information.

Collect less

Does ClinicQ need the symptom, or only the service?

Tell users

A short privacy notice at sign-up

Keep it short

Delete or anonymize old tickets on a schedule

Data subjects have rights, including to be informed, to access, to correct and to erasure. Plan how a user exercises them.

Republic Act No. 10173, Data Privacy Act of 2012 · National Privacy Commission (privacy.gov.ph)

22

The Philippine Data Privacy Act sets the three general principles on the slide and classifies health information as sensitive personal information, which needs stronger justification and protection. The National Privacy Commission enforces it. For a student MVP the practical steps are: minimize what is collected, write a plain privacy notice, restrict access with the authorization rules from today, encrypt in transit with HTTPS, and define retention. The JSONB intake answers from Week 7 are exactly the kind of data to question. This is general guidance, not legal advice; a real clinic deployment would involve the university's data protection officer.

Start with the Week 2 starter app everyone already has. Ask: what happens to the tickets if I press Ctrl+C and run flask again? In debug mode the reloader restarts the process on every file save, so the data disappears even during development. Production servers like Gunicorn run several worker processes, each with its own memory, so users would see different queues. Persistence

Why PostgreSQL for ClinicQ

Definition

PostgreSQL is an open-source relational database: data lives in tables of rows and columns, linked by keys and queried with SQL.

Reliable

ACID transactions: a write either fully happens or not at all

Standard SQL

What you learn transfers to MySQL, SQL Server, SQLite

Rich types

Dates, enums, arrays, JSONB, full-text search

Free and open

Used by startups and governments; runs anywhere

PostgreSQL Global Development Group, postgresql.org/about

04

Relational databases have been the default for business data for decades because they enforce structure and correctness. ACID stands for atomicity, consistency, isolation and durability; we will use transactions in Week 5. PostgreSQL also gives us features we need later in the course: JSONB and full-text search in Week 7. Alternatives worth naming: SQLite is a single file and great for tests or tiny apps but weak with many concurrent writers; MySQL is also fine; MongoDB is a document database without enforced relations. For a queue where correctness matters, a relational database is the right fit.

Analogy: an image is a class, a container is an object made from it. The key idea for databases is the volume: containers are disposable, but the data directory is mounted on a named volume, so deleting and recreating the container keeps the data. Students need Docker Desktop on Windows or macOS (WSL 2 backend on Windows) or Docker Engine on Linux. If a laptop cannot run Docker, a local PostgreSQL install is an acceptable fallback; the Flask code does not change, only the connection string.

Docker Compose describes the services an app needs in one file that lives in the repository. Compose automatically reads a .env file in the same folder and substitutes the variables. The official postgres image creates the user and database from the three environment variables the first time the volume is empty. CCC181 · Week 4 · PostgreSQL, Docker and data persistence

12

Types are the first line of data validation. Use timestamptz, timestamp with time zone, for moments in time so the clinic's local time and the server's UTC never get mixed up. Never store dates or numbers as text. Constraints are guarantees: even if a buggy route or a manual psql session tries to insert bad data, PostgreSQL rejects it. A CHECK constraint or a PostgreSQL enum type can restrict status values; the CHECK is easier to change later through a migration.

Row 15 shows the problem: someone typed the email and service differently, and now reports count Ana twice and Consultation as two services. These are update anomalies. Normalization removes them by storing each fact once and linking with keys. For this course, aim for third normal form; a simple test is: if you would have to update the same fact in more than one row, split it into its own table. Relationships

Three kinds of relationships

One-to-many

One service has many tickets. The foreign key goes on the many side: tickets.service_id.

Many-to-many

Staff can work many services; a service has many staff. Needs a join table: staff_services(user_id, service_id).

One-to-one

A user has one profile. A foreign key that is also UNIQUE: profiles.user_id.

Most common

One-to-many covers most MVP data: a post's comments, an order's items, a service's tickets.

On delete

Decide what happens to children: block it, cascade, or set to null. ON DELETE RESTRICT is the safe default.

CCC181 · Week 4 · PostgreSQL, Docker and data persistence

14

Every relationship in an ERD is one of these three. The many-to-many case cannot be stored with a single foreign key, so it becomes its own table with two foreign keys, and that table can carry extra columns like the date a staff member was assigned. Discuss delete behavior with the ClinicQ example: should deleting a service delete all its historical tickets? No, that would destroy reports, so restrict the delete or mark the service inactive instead. Ask students to label each line in their ERD with its kind.

An object-relational mapper translates between Python objects and rows. We use Flask-SQLAlchemy, a thin Flask integration over SQLAlchemy 2.0. Benefits: queries are built from Python, values are always sent as bound parameters, which prevents SQL injection, and results are objects that templates can use directly. SQLAlchemy

Defining the Ticket model

from datetime import datetime
from flask_sqlalchemy import SQLAlchemy
from sqlalchemy import ForeignKey, String, func
from sqlalchemy.orm import Mapped, mapped_column

db = SQLAlchemy()

class Ticket(db.Model):
    __tablename__ = "tickets"
    id: Mapped[int] = mapped_column(primary_key=True)
    status: Mapped[str] = mapped_column(String(20), default="waiting")
    created_at: Mapped[datetime] = mapped_column(server_default=func.now())
    called_at: Mapped[datetime | None]
    user_id: Mapped[int] = mapped_column(ForeignKey("users.id"))
    service_id: Mapped[int] = mapped_column(ForeignKey("services.id"))

CCC181 · Week 4 · PostgreSQL, Docker and data persistence

16

This is the SQLAlchemy 2.0 typed style. Each attribute annotated with Mapped becomes a column; the type annotation decides the SQL type and nullability. called_at is nullable because a waiting ticket has not been called yet. default runs in Python when the object is created; server_default becomes part of the table definition, so rows inserted from psql get it too. In app.py, import db from models and call db.init_app(app) after setting SQLALCHEMY_DATABASE_URI. Keeping db in models.py avoids circular imports.

Why not db.create_all()?

It only creates missing tables. It never adds a column to a table that already exists, and it keeps no history.

Team benefit

Anyone who pulls your branch runs flask db upgrade and gets the same schema.

Flask-Migrate documentation · Alembic autogenerate documentation

18

Flask-Migrate wraps Alembic, the migration tool for SQLAlchemy. A migration is a small Python script with upgrade and downgrade functions. The scripts form an ordered chain stored in migrations/versions and committed to Git, exactly like source code. This is how a schema evolves safely across laptops, the instructor's machine and the deployed server. The review step matters: autogenerate cannot detect a renamed column, it sees a drop and an add, which would delete data.

Map each operation to its SQL statement, its SQLAlchemy call and its route. CRUD operations

Create: joining the queue

app.py

@app.post("/join")
def join():
    email = request.form.get("email", "").strip().lower()
    service_id = request.form.get("service_id", type=int)
    service = db.session.get(Service, service_id) if service_id else None
    if "@" not in email or service is None:
        flash("Enter your school email and pick a reason.", "danger")
        return redirect(url_for("join_form"))
    user = db.session.scalar(db.select(User).filter_by(email=email))
    if user is None:
        user = User(email=email, name=request.form.get("name", ""))
    ticket = Ticket(user=user, service=service)
    db.session.add(ticket)
    db.session.commit()
    return redirect(url_for("ticket", ticket_id=ticket.id))

def ticket(ticket_id):

@app.get("/staff")
def staff():
    stmt = (db.select(Ticket)
            .filter_by(status="waiting")
            .order_by(Ticket.created_at))
    waiting = db.session.scalars(stmt).all()
    return render_template("staff.html", tickets=waiting)

@app.post("/staff/tickets/<int:ticket_id>/serve")
def serve(ticket_id):
    t = db.get_or_404(Ticket, ticket_id)
    t.status = "served"

@app.post("/queue/<int:ticket_id>/leave")
def leave(ticket_id):
    t = db.get_or_404(Ticket, ticket_id)
    t.status = "left"   # soft delete keeps history
    db.session.commit()
    return redirect(url_for("index"))

Update

Load the object, change attributes, commit. SQLAlchemy writes only the changed columns.

Hard or soft delete?

db.session.delete(t) removes the row. Changing the status keeps it for reports and audits.

Validate in three layers

1 · Browser

required, type="email", maxlength. Fast feedback, but easy to bypass.

2 · Flask

Check types, ranges, formats and permissions. The real gatekeeper; return a clear message.

3 · Database

NOT NULL, UNIQUE, CHECK, foreign keys. The last line of defense against any bug.

try:
    db.session.commit()
except IntegrityError:
    db.session.rollback()

Same rule, three places: the browser is for users, Flask is for security, the database is for integrity.

This answers last week's Q4 again with the database added. The browser checks help honest users; anyone can send a request with curl or Postman and skip them. Flask validation is required for every input. Database constraints catch what slips through, including race conditions such as two requests creating the same email at the same moment. When the database rejects a commit, SQLAlchemy raises IntegrityError and the session must be rolled back before it can be used again. Libraries like WTForms or marshmallow can organize validation; plain checks are fine for the MVP.

Expected answers. Q1: memory is lost on restart, each worker process has its own copy, and nothing coordinates concurrent writes. Q2: down removes the container but keeps named volumes, so data survives; down -v also removes the volumes and deletes the data. Q3: position is derived data that changes whenever anyone joins or leaves; storing the creation time is a fact that never changes, and position can always be computed from it, so it is never out of date. Q4: two requests can pass the Flask check at the same moment, other code paths or manual edits can skip Flask, and the database constraint is the only check that is guaranteed to run for every write.

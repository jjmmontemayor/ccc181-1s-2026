REST APIs

REST: an architectural style for the web

Definition

REST (Representational State Transfer) models an API as resources identified by URLs, manipulated through a uniform interface of HTTP methods, exchanging representations such as JSON.

Client–server

UI and data storage evolve separately

Stateless

Each request carries everything needed; no server memory of the last one

Cacheable

Responses say whether they can be reused

Uniform interface

Same methods, URLs and status codes everywhere

Roy T. Fielding, Architectural Styles and the Design of Network-based Software Architectures (2000), ch. 5

04

REST was described by Roy Fielding in his 2000 doctoral dissertation as the style behind the web's success. A resource is a thing, such as a ticket; a representation is a snapshot of it, such as a JSON object. Statelessness is the constraint students most often break: the server must not rely on remembering what this client did before, so authentication tokens and paging parameters travel with every request. Most real-world JSON APIs are REST-like rather than strictly RESTful, and that is fine for this course as long as they are consistent.

Safe

Does not change anything on the server. Clients may call it freely, prefetch it, cache it.

Idempotent

Doing it twice has the same effect as once. Clients may safely retry on a timeout.

RFC 9110, HTTP Semantics (2022), sections 9.2.1 and 9.2.2

06

These properties come from the HTTP specification, RFC 9110, and clients rely on them. Idempotency matters a lot for mobile apps on bad networks, which we meet in Week 10: if a DELETE times out, retrying is harmless, but retrying a POST may create a second ticket. That is one reason the Week 4 PRG pattern and the Week 3 disabled button exist. PATCH is idempotent when it sets values, such as status to served, and not when it increments something.

RFC 9110, HTTP Semantics (2022), section 15

07

The status code is the first thing a client checks, before parsing the body. A common student mistake is returning 200 with a body like {"error": "not found"}; the client then treats a failure as success. 400 versus 422: 400 when the request cannot be parsed at all, 422 when it parses but the values fail validation. 409 fits ClinicQ well: trying to serve a ticket that has already left the queue conflicts with its current state. A 500 should never be caused by bad input; if it is, that is a missing validation.

08

Read the raw HTTP once so the tools stop being magic: a method and path, headers, a blank line, then the body. Content-Type tells each side how to parse the body. JSON has strings, numbers, booleans, null, arrays and objects; dates have no JSON type, so we send ISO 8601 strings with a time zone offset. The response returns the created resource, including server-generated fields such as id, status and position, so the client does not need a second request.

10

Consistency matters more than any single rule. Versioning is important for mobile clients in particular: once an app is installed on phones, you cannot force every user to update, so old clients keep calling the old URLs. Lists should never return unlimited rows; a default limit protects the database and the phone's data plan. Pick a naming style once; snake_case matches Python and PostgreSQL, while camelCase matches JavaScript and Dart; Week 10 shows how Dart maps either.

A blueprint keeps API routes separate from the HTML routes while sharing the same models and helpers, including the Week 5 queue_position query. Since Flask 2.2, returning a dict or a list from a view produces a JSON response automatically. The serializer function matters: it decides exactly which fields leave the server. Never return model objects or all columns directly, because you might leak fields like password hashes later. In a list, calling queue_position per ticket is an N+1 pattern; a better version computes positions with one window-function query, which is a good Week 7 performance exercise.

@api.post("/tickets")
def create_ticket():
    data = request.get_json(silent=True)
    if data is None:
        return problem(400, "Body must be JSON.")
    errors = validate_ticket(data)
    if errors:
        return problem(422, "Invalid ticket.", errors)
    t = Ticket(user=get_or_create_user(data["email"]),
               service_id=data["service_id"])
    db.session.add(t)
    db.session.commit()
    return ticket_json(t), 201, {
        "Location": url_for("api.get_ticket", ticket_id=t.id)}

This mirrors the Week 4 join route, with JSON instead of a form and status codes instead of redirects. The three-part return value is Flask's tuple form: body, status code, headers. The Location header points to the new resource. problem() is a small helper we define on the error-handling slide so every error looks the same. get_or_create_user is the email lookup from the Week 4 join route moved into a helper, so the web form and the API share it; in Week 11 the logged-in user replaces the email field. Ask: what should happen if service_id refers to a service that does not exist? The validator catches it and returns 422 rather than letting the foreign key constraint raise a 500.

Updating and deleting

api.py

NEXT = {"waiting": {"called", "left"},
        "called":  {"served", "waiting"}}
@api.patch("/tickets/<int:ticket_id>")
def update_ticket(ticket_id):
    t = db.get_or_404(Ticket, ticket_id)
    new = (request.get_json(silent=True) or {}).get("status")
    if new not in NEXT.get(t.status, set()):
        return problem(409, f"Cannot go from {t.status} to {new}.")
    t.status = new
    db.session.commit()
    return ticket_json(t)
@api.delete("/tickets/<int:ticket_id>")
def delete_ticket(ticket_id):
    db.session.delete(db.get_or_404(Ticket, ticket_id))
    db.session.commit()
    return "", 204

Business rules on the server

The allowed status changes live in one dictionary, used by every client.

204 means empty

Return an empty body; the client already knows what it deleted.

CCC181 · Week 6 · REST API development and midterm demonstration

13

The NEXT dictionary is a tiny state machine: a ticket can go from waiting to called or left, and from called to served or back to waiting if the student did not show up. Anything else is a 409 Conflict, because the request is valid but contradicts the ticket's current state. This is exactly the kind of rule that must not live only in a client, since a modified client could skip it. In the real app the called transition should use the Week 5 locking query. Delete returns 204 with no body.

Validation

Validate input and say exactly what is wrong

validators.py

def validate_ticket(data):
    errors = {}
    sid = data.get("service_id")
    if not isinstance(sid, int):
        errors["service_id"] = "Required integer."
    elif db.session.get(Service, sid) is None:
        errors["service_id"] = "No such service."
    if "@" not in str(data.get("email", "")):
        errors["email"] = "Enter a school email."
    return errors

Validation rules from Week 3 and Week 4 still apply: the server checks everything, whatever the client did. Returning errors keyed by field name lets the web page or the Flutter form show the message next to the right input instead of a generic failure. Error handling

One error format for the whole API

api.py

from werkzeug.exceptions import HTTPException

def problem(status, title, errors=None):
    body = {"title": title, "status": status}
    if errors:
        body["errors"] = errors
    return body, status

@api.errorhandler(HTTPException)
def http_error(e):
    return problem(e.code, e.name)   # 404, 405, ...

@api.errorhandler(Exception)
def server_error(e):
    current_app.logger.exception(e)
    return problem(500, "Something went wrong.")

Consistent

Clients write one error handler, not one per endpoint

Never leak internals

No stack traces or SQL in responses; log them on the server

A standard exists

RFC 9457 Problem Details uses title, status, detail

RFC 9457, Problem Details for HTTP APIs (2023)

15

Without these handlers, a 404 from get_or_404 inside the API returns Flask's HTML error page, which a mobile app cannot parse. The blueprint error handlers convert every HTTP error into the same JSON shape, and the catch-all logs the real exception for you while returning a generic message to the client. In debug mode Flask shows the interactive traceback instead; never run debug mode on a deployed server. RFC 9457 standardizes this format with the media type application/problem+json; following its field names is a good habit.

Endpoint design

Lists: filter, sort and page

api.py

@api.get("/tickets")
def list_tickets():
    status = request.args.get("status", "waiting")
    limit = min(request.args.get("limit", 20, type=int), 100)
    offset = request.args.get("offset", 0, type=int)
    base = db.select(Ticket).filter_by(status=status)
    total = db.session.scalar(
        db.select(func.count()).select_from(base.subquery()))
    items = db.session.scalars(
        base.order_by(Ticket.created_at, Ticket.id)
            .limit(limit).offset(offset)).all()
    return {"items": [ticket_json(t) for t in items],
            "total": total, "limit": limit, "offset": offset}

Cap the limit

min(…, 100) stops clients asking for a million rows

Stable order

Paging without ORDER BY returns random pages

Return metadata

total lets the app show “page 2 of 5”

This upgrades the list endpoint from the earlier slide. The type=int argument converts query parameters and falls back to the default on bad input. Ordering is mandatory for pagination, with the id tiebreaker from Week 5. Offset pagination is simple and fine for MVPs; for very large or fast-changing tables, keyset pagination using created_at and id is faster, which is a Week 7 topic. Wrapping the list in an object with items and total also leaves room to add fields later without breaking clients.

Class discussion

Questions to discuss

Q1

Why is GET /deleteTicket?id=12 a dangerous design?

Q2

When should an API return 422 instead of 400, and when 409?

Q3

Why must the server validate input even if the Flutter app validates too?

Q4

A POST times out on a bad network. Why is retrying risky, and a DELETE retry is not?

CCC181 · Week 6 · REST API development and midterm demonstration

25

Expected answers. Q1: GET is defined as safe, so browsers, link previews and crawlers may call it automatically and delete data; it also hides the action from the method. Q2: 400 when the request cannot be parsed, such as invalid JSON; 422 when it parses but values are invalid; 409 when the request is valid but conflicts with the resource's current state, such as serving a ticket that already left. Q3: any client can be modified or replaced by a tool such as Postman, so only server-side checks are guaranteed. Q4: POST is not idempotent, so a retry may create a second ticket; DELETE is idempotent, so a repeat has the same effect as one call.

03

Every network call returns a Future, the Dart equivalent of a JavaScript Promise or the Python coroutine from Week 7. await pauses the current function until the value arrives, without blocking the event loop, so animations and taps keep working. Errors thrown inside an async function surface at the await, so normal try and catch works. Forgetting await is the classic bug: the code continues with a Future instead of the value, and the linter's unawaited_futures rule catches it.

class _ServicesState extends State<ServicesList> {

FutureBuilder rebuilds when the Future completes and gives a snapshot with the connection state, data or error. The trap: build can run many times per second during animations, so calling the repository inside build sends a new request each time. Create the Future once in the State, as here, or keep the result in the Week 9 model and let the screen watch it, which is usually the better choice for app state. Use FutureBuilder for simple, screen-local loads.

A Stream delivers values over time: Firestore snapshots in Week 9, a text field's changes, or this polling loop that refreshes Ana's position every 20 seconds, the interval suggested in Week 7. An uncaught error inside the generator would end the stream, so failures are caught inside the loop and the UI keeps showing the last good value. HTTP

import 'dart:convert';
import 'package:http/http.dart' as http;

const baseUrl = String.fromEnvironment('API_URL',
    defaultValue: 'http://10.0.2.2:5000/api/v1');

Future<Ticket> fetchTicket(http.Client client, int id) async {
  final res = await client
      .get(Uri.parse('$baseUrl/tickets/$id'),
           headers: {'Accept': 'application/json'})
      .timeout(const Duration(seconds: 10));
  if (res.statusCode == 200) {
    return Ticket.fromJson(jsonDecode(res.body) as Map<String, dynamic>);
  }
  throw ApiException.fromResponse(res);
}

class Ticket {

      required this.service, this.position, required this.createdAt});
  final int id;
  final String status;
  final String service;
  final int? position;
  final DateTime createdAt;

08

jsonDecode returns dynamic maps and lists; the fromJson factory turns them into a typed, immutable object so the rest of the app gets compile-time checking. Each cast documents what the API promises; if the server sends something different, the cast throws a TypeError at the boundary instead of a confusing bug deep in a widget. position is nullable because served tickets have no position. ISO 8601 strings from Flask parse directly with DateTime.parse. Keep these models in sync with the API documentation from Week 6.

Repository

ApiTicketRepository replaces the fake

lib/data/api_ticket_repository.dart

class ApiTicketRepository implements TicketRepository {
  ApiTicketRepository(this._client);
  final http.Client _client;
  static const _json = {'Content-Type': 'application/json'};

  @override
  Future<Ticket> join(String email, int serviceId) async {
    final res = await _client
        .post(Uri.parse('$baseUrl/tickets'), headers: _json,
              body: jsonEncode({'email': email, 'service_id': serviceId}))
        .timeout(const Duration(seconds: 10));
    final body = jsonDecode(res.body) as Map<String, dynamic>;
    return switch (res.statusCode) {
      201 => Ticket.fromJson(body),
      422 => throw ValidationException(Map<String, String>.from(body['errors'])),
      _   => throw ApiException(res.statusCode, body['title'] as String?),
    };
  }
  // fetch() and leave() follow the same pattern
}

REST is stateless, so the client proves who it is on every request, usually with a bearer token in the Authorization header. The Flask side, issuing and checking tokens and deciding who may do what, is built in Week 11; this slide prepares the client. Store the token in flutter_secure_storage, which uses the Android Keystore and iOS Keychain. Handle 401 in one place, in the API client or a Dio interceptor, by clearing the token and sending the user to the login screen. Over plain HTTP the token can be intercepted, which is one more reason the deployed API must use HTTPS.

API auth

The same with a Dio interceptor

lib/data/dio_client.dart

final dio = Dio(BaseOptions(
  baseUrl: baseUrl,
  connectTimeout: const Duration(seconds: 5),
  receiveTimeout: const Duration(seconds: 10),
));

dio.interceptors.add(InterceptorsWrapper(
  onRequest: (options, handler) async {
    final token = await storage.read(key: 'token');
    if (token != null) options.headers['Authorization'] = 'Bearer $token';
    handler.next(options);
  },
  onError: (e, handler) async {
    if (e.response?.statusCode == 401) await storage.delete(key: 'token');
    handler.next(e);
  },
));

final res = await dio.get('/tickets/57');   // res.data is already decoded

For students who choose Dio, interceptors put cross-cutting concerns in one place: the token is attached to every request and a 401 clears it, without repeating code in each repository method. Dio throws a DioException for non-2xx responses by default, with the response attached, so the repository catches DioException and maps it to the app's error types. Logging interceptors such as LogInterceptor help during development but must not log tokens in production builds.

Exceptions

One place that maps exceptions

lib/data/errors.dart

class AppError implements Exception {
  const AppError(this.message);
  final String message;
}

Future<T> guard<T>(Future<T> Function() call) async {
  try {
    return await call();
  } on SocketException {
    throw const AppError('You seem to be offline.');
  } on TimeoutException {
    throw const AppError('ClinicQ is taking too long. Try again.');
  } on http.ClientException {
    throw const AppError('Could not reach ClinicQ.');
  } on FormatException {
    throw const AppError('Unexpected reply from the server.');
  }
}

Wrap each repository call: guard(() => _join(email, id))

Centralizing the mapping means screens and state never deal with SocketException or status codes, only with AppError messages and ValidationException. Catching specific types is important: a blanket catch that hides every error would also hide programming mistakes like a null check failure, making bugs invisible. Full offline support with synchronization is a big project; offline-aware behavior is achievable: the app never shows a blank or frozen screen when the network drops. Offline-aware

Falling back to the cached ticket

lib/data/cached_ticket_repository.dart

Future<Ticket> fetch(int id) async {
  try {
    final t = await guard(() => _api.fetch(id));
    await _prefs.setString('ticket_$id', jsonEncode(t.toJson()));
    await _prefs.setString('ticket_${id}_at', DateTime.now().toIso8601String());
    return t;
  } on AppError {
    final saved = _prefs.getString('ticket_$id');
    if (saved == null) rethrow;            // nothing cached: show the error
    return Ticket.fromJson(jsonDecode(saved))
        .copyWith(isStale: true);          // UI shows "offline · updated …"
  }
}

The repository tries the network first, saves each success with a timestamp, and on failure returns the cached copy marked as stale.

CCC181 · Week 9 · Flutter state management and data services

04

You can share state with plain setState by lifting it to a common ancestor and passing values and callbacks down through every constructor. It works for two or three screens, then becomes painful: middle widgets pass data they do not use, and a change at the top rebuilds everything below. The solutions all follow the same idea: keep shared state in an object outside the widgets, make it available to any descendant, and notify only the widgets that depend on it.

This is the revised mobile architecture the milestone asks students to document. Each layer has one job and only talks to the one below it. The UI renders state and forwards taps. The state layer holds what the app currently knows, such as the ticket, loading and error, and decides what happens on each action. The repository hides where data comes from, so today it can be fake data and next week the REST API without changing any screen. It parallels the separation students already have in Flask.

06

Provider wraps Flutter's built-in InheritedWidget mechanism in a friendlier API and is the approach the Flutter documentation uses in its simple app state guide. The cycle in the middle row is the whole idea. watch is for build methods, because the widget should redraw when the model changes; read is for event handlers, because a button callback only needs to call a method and should not cause rebuilds. Riverpod fixes some of Provider's limitations, such as not depending on BuildContext, and is acceptable if a student prefers it.

Provider

A ChangeNotifier for the ticket

lib/state/ticket_model.dart

class TicketModel extends ChangeNotifier {
  TicketModel(this._repo);
  final TicketRepository _repo;
  Ticket? ticket;
  bool loading = false;
  String? error;

  Future<void> join(String email, int serviceId) async {
    loading = true; error = null;
    notifyListeners();
    try {
      ticket = await _repo.join(email, serviceId);
    } catch (_) {
      error = 'Could not join. Try again.';
    } finally {
      loading = false;
      notifyListeners();
    }
  }
}

Holds three things

The data, whether it is loading, and any error

Notify twice

Once to show loading, once with the result

No widgets here

Pure Dart: easy to test

Cubit

Methods that emit new states. Less code; start here.

Bloc

Explicit event classes mapped to states. More code, full traceability.

Package

flutter_bloc, with bloc_test for tests.

bloclibrary.dev · pub.dev/packages/flutter_bloc

09

BLoC stands for Business Logic Component. Instead of mutable fields and notifyListeners, a Cubit emits a sequence of immutable state objects, and the UI rebuilds for each one. That makes every possible screen state explicit, which pairs well with the Week 3 idea of designing every state. A Bloc adds event classes for each user action, useful in large teams because every change is traceable; for an MVP, Cubit is enough. The library is flutter_bloc on pub.dev.

BLoC

The same feature as a Cubit

lib/state/ticket_cubit.dart

sealed class TicketState {}
class TicketIdle extends TicketState {}
class TicketLoading extends TicketState {}
class TicketJoined extends TicketState { TicketJoined(this.ticket); final Ticket ticket; }
class TicketError extends TicketState { TicketError(this.message); final String message; }
class TicketCubit extends Cubit<TicketState> {
  TicketCubit(this._repo) : super(TicketIdle());
  final TicketRepository _repo;
  Future<void> join(String email, int serviceId) async {
    emit(TicketLoading());
    try {
      emit(TicketJoined(await _repo.join(email, serviceId)));
    } catch (_) {
      emit(TicketError('Could not join. Try again.'));
    }
  }
}

Compare with the ChangeNotifier version: instead of three independent fields that could contradict each other, there are four state classes and the app is always in exactly one, so it can never be loading and showing an error at the same time by accident. The sealed modifier from Dart 3 lets the compiler know every possible state and check that the UI handles each one, shown on the next slide. emit replaces notifyListeners. The repository injection is identical, so the Week 10 REST repository works with either approach.

11

A switch expression over a sealed class must be exhaustive, so adding a new state such as TicketServed later produces a compile error everywhere it is not handled. The :final ticket syntax is a Dart 3 pattern that extracts the field. Calling the cubit from a button looks like context.read<TicketCubit>().join(email, serviceId), the same as Provider. This exhaustiveness is BLoC's main teaching advantage.

The milestone mentions Firebase or an approved data-service integration. In this course the Flask and PostgreSQL API remains the source of truth for the app's main data, because students built and tested it. Local data

Remember Ana's ticket across restarts

lib/state/ticket_model.dart

class TicketModel extends ChangeNotifier {
  Future<void> restore() async {
    final prefs = await SharedPreferences.getInstance();
    final id = prefs.getInt('ticket_id');
    if (id == null) return;
    ticket = await _repo.fetch(id);
    notifyListeners();
  }

  Future<void> _save() async {
    final prefs = await SharedPreferences.getInstance();
    await prefs.setInt('ticket_id', ticket!.id);
  }
}

1

After joining, call _save()

2

On app start, call restore()

3

Fetch fresh data for that id; don't trust the stored copy

On leave or served, prefs.remove(&#39;ticket_id&#39;).

Repositories

A repository hides where data comes from

lib/data/ticket_repository.dart

abstract class TicketRepository {
  Future<Ticket> join(String email, int serviceId);
  Future<Ticket> fetch(int id);
  Future<void> leave(int id);
}

class FakeTicketRepository implements TicketRepository {
  int _next = 57;
  @override
  Future<Ticket> join(String email, int serviceId) async {
    await Future.delayed(const Duration(milliseconds: 600));
    return Ticket(id: _next++, status: 'waiting', position: 4);
  }
  @override
  Future<Ticket> fetch(int id) async =>
      Ticket(id: id, status: 'waiting', position: 4);
  @override
  Future<void> leave(int id) async {}
}

Expected answers. Q1: the search box text is ephemeral, used by one widget; the logged-in user is app state, needed by many screens and across sessions.
